## Repo 與發布狀態

這個 repo 有兩個相接但分開維護的產品：

1. `site/`：Astro 靜態網站「百冊 · One Hundred」。書籍資料與已發布心得以 `site/src/content/books/` 為單一真實來源。
2. `book-reader/`：書稿、心得與生命素材；`docs/book-v2-pipeline.sh` 負責逐章寫作流水線。

書稿有兩份，不互相覆蓋：

- `book-reader/book/`：v1 完稿，保留作為既有版本。
- `book-reader/book-v2/`：目前持續修訂、也是網站 `/manuscript` 閱讀器實際取用的版本。`site/scripts/manuscript-reader.mjs` 的來源目錄指向這裡。

book-v2 一章一檔，另有 `_continuity.md`（跨章事實與資訊邊界）及 `_feedback/`（場景表、讀者、編輯、潤飾與稽核證據）。

## 當前核心問題：人物聲音晚於書稿進入流程

`book-reader/is-me/` 的人物資料是在全書已有稿之後才真正進入 editor 與 polish。這代表「流程現在會讀人物資料」不能證明既有十五篇已經照人設寫成；全書也不能靠補幾種小動作或把性格特徵平均灑進各章來補救。

目前要驗證的是每章原本已經成立的人物基準：他怎麼注意、怎麼答非所問、怎麼認錯、怎麼把照顧放進安排、什麼時候會反駁，以及哪些成熟度在當時還不能出現。修改前後都要做回歸，防止修順句子時把原有的人味磨平。

第七章原先的優先風險是事件與任務很多，男主角容易只剩功能。本輪四處局部補寫已通過作者校閱；後續全書重讀仍須檢查人物聲音是否跨章成立，不能只憑這四處推定問題已解決。

人物判讀的依據順序：

1. 作者當輪裁定與親手修改的句子
2. 本章章卡與 `_continuity.md`
3. `book-reader/is-me/` 的人物資料，以及 `_feedback/全書-人物弧線.md` 的時間分層與「不能提早出現」
4. `_feedback/全書-手改對照.md` 的完整 before／after 樣本
5. [book-v2-workflow.md](book-v2-workflow.md) 的修稿偏好

條文只能幫忙排除錯法，不能取代對原稿和親筆句的閱讀。

## 現行操作邊界

- Rui-Xuan 寫作與 book-v2 正文修改只從 `.agents/skills/rui-xuan-book-v2/SKILL.md` 進入；直接動正文時再載入 `references/book-v2-direct-edit.md`。
- 流水線為寫作／讀者／編輯／潤飾／稽核五步。讀者保持盲讀；editor 先從現稿引用建立人物基準；polish 保存步驟開始前快照並做人物回歸。
- 直接修改正文時，必須同一輪實際讀原檔並先交出附行號逐字引文。由來見 [decisions/book-v2-動筆前規範.md](decisions/book-v2-動筆前規範.md)。
- 書稿只有在作者人工校閱並明確同意後才 commit；逐一指定檔案，不用 `git add -A`。
- 第 05、08、12、13、14 章的歷史 `hand edit` 自動抽取範圍受到首次入庫或大量新增污染。若再跑流程，先用 `_feedback/全書-手改對照.md` 與章級回饋核實歸屬；`_feedback/全書-作者手改句.md` 只作 Git 來源候選，不能把整章當成作者手改，也不再逐字鎖定。
